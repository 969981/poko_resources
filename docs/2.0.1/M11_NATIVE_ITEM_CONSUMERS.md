# M11 — 原生 2.0.1 ExeFS 物品记录加载器与消费者数据流

## 范围与证据门槛

在 M10 SQLite 原始字段证据图的基础上，启动对 `2.0.1/exefs/main` 的原生 ARM64 数据流逆向。**该阶段首先做寄存器别名排除、真实指令解码和候选函数分级，尚不把汇编常数/同位移自动宣称为已定位物品加载器。**

原始源 SHA：

- `main`：`8a8ce87b4edfce88c6260da5dd80d6cafc03a761eebc842d7a3476e353a8336f`
- 物品原始表 `00983.bin`：`2a2dbc88715dc76410cef495d418613456c0c4fa7b7d719e7b37709ad53e1b6f`
- `00983.bin`：头 64 字节，4,600 项，68 字节一项；`+0x22` 为已证明名称索引；`+0x26/+0x3A` 为待证明的分组字节。

## 实现

`Scripts/resources/trace_native_item_provenance.py` ：

1. 严格 SHA/NSO0 解压原版 ExeFS 并逐条枚举 AArch64 text 的所有 4 字节指令位。
2. 扫描精确内存读取 `ldrh [Xn,#0x22]`、`ldrb [Xn,#0x26]` 和 `ldrb [Xn,#0x3A]`，记录指令原字、原生 text RVA、目标与基址寄存器。
3. 在局部窗口内进行 **同一基址寄存器** 检查，跨基本块跳转、函数调用和写入基址寄存器的情况不算连续共同访问。
4. 回溯基址寄存器在局部直线代码中的最近定义，保存所在 RVA、反汇编、四字节指令原文；超过窗口或遇分支，显式标为未解析。
5. 对 `cmp #99/#100/#255` 检查参与比较的寄存器是否真来自 `+0x26` 读取；不能把单纯位置相近等价为数量逻辑。
6. 同时扫描 `68/983/4600` 近邻立即数，只用作下一轮原生调用链定位的优先级线索，不视为真实物品表加载路径。
7. 输出 `item_consumer_register_provenance.json` 和紧凑候选列表到 Actions artifact；不自动把原版资产或大型反汇编提交到 Git。

`tests/test_trace_native_item_provenance.py` 包含源字段读取、同基址共同访问、无关比较、基本块分支和基址寄存器重定义的独立正反例。

## 下一步必须完成的跨函数链

`00983.bin 原始表解析 → 分配/拷贝 68 字节表项 → ID 索引寻址 → consumer+0x26/+0x3A → 枚举分发`

对堆叠则需独立追踪：

`背包新增 → 相同 itemID 槽比较 → 当前 Count → 剩余数量 → 99/100 条件 → 溢出/新槽/拒绝 → 写回`

如果一个候选函数的 `+0x26` 基址尚未与 00983 原生加载器关联，不得升格为物品分类，即使同时包含 `cmp #99`。近邻常数 `4600` 和 `68` 也必须恢复寄存器计算和循环边界，不能仅看文本距离。

M11 不修改现有 Python 解包、PNG、九语言、CSV 或 SQLite 输出，也不对 M10 已有候选外键添加语义标签。

## 首轮原版汇编结果（对全 text 执行）

扫描 `10,298,656` 条 ARM64 指令槽，找到 `ldrh +0x22` 410 条、`ldrb +0x26` 1,804 条、`ldrb +0x3A` 333 条。

经过相同基址寄存器、控制流未跳转、基址未重写的检查后，**仅剩 6 处局部共访问候选**，其中 `main+0x5E7F4C` 同时伴随 `+0x22` 与 `+0x3A`。反汇编证明这些上下文全部是**字段搬运/转换**，没有在其紧邻语句执行分类枚举判断：

| NSO text RVA | 原始 byte load | 同步写入 | 本轮结论 |
| --- | --- | --- | --- |
| `0x5E7F4C` | `ldrb w9,[x0,#0x26]` | `strb w9,[x1,#0x26]` | 结构复制；`+0x22` 为邻接复制，不证明 Item |
| `0x382C24` | `ldrb w8,[x20,#0x26]` | `strb w8,[x19,#0x70C]` | 结构映射/搬运 |
| `0x5D0CC4` | `ldrb w9,[x23,#0x26]` | `strb w9,[x8,#0x26]` | 结构复制 |
| `0x5D0E38` | `ldrb w9,[x23,#0x26]` | `strb w9,[x8,#0x26]` | 结构复制 |
| `0x5E8CF4` | `ldrb w8,[sp,#0x26]` | `strh w8,[x20,#0x240]` | byte→halfword 转换 |
| `0x672D48` | `ldrb w10,[x13,#0x26]` | `strb w10,[x12,#0x26]` | 结构复制 |

即使出现 `+0x22/+0x26/+0x3A` 的强局部相关，也可能只是物理内存复制。本轮 6 处均没有近邻 `cmp #99/#100`、`movz #68` 或 `cmp/movz #4600`。不能直接升级 `+0x26` 的语义。

### M11.2 的更精确入口

`trace_native_item_decisions.py` 改从全部 1,804 条 `ldrb +0x26` 及 333 条 `ldrb +0x3A` 出发，追踪**实际加载的寄存器**是否在后续直线代码中参与 `CMP/CMN/TST/CBZ/CBNZ/TBZ/TBNZ`。不同寄存器、调用/分支阻断或寄存器改写均被排除；立即 `STRB/STRH` 数据搬运独立记录，不当成分类检查。原版执行输出与聚合报告作为 CI artifact 提供。

直接证明原始字节参与比较，也**不等于**证明其基址是 `00983.bin` 的 Item 记录。若要正式升级物品类型，必须跨函数恢复源表加载、ID 索引和分类分发关系。

## M11.2 原版条件消费者的已执行统计

`.github/workflows/unpack-m11-item-provenance.yml` 对原版 SHA 完整读取后得到以下静态数据：

| 条件 | +0x26 | +0x3A |
| --- | ---: | ---: |
| 原版 LDRB 站点 | 1,804 | 333 |
| 寄存器在随后直线代码进入 CMP/CMN/TST/CBZ/TBZ 等条件操作 | 1,677 | 178 |
| LDRB 后立即显式存储 | 17 | 77 |

共 **1,855 个**局部条件消费者候选。这里按读取指令 PC 计数，**不是 1,855 个不同函数/物品枚举**；一个字段在许多无关类型中可能重复出现。完整候选位于 CI 的 `field_condition_dataflow.json`，只保留证据，不声称跨函数关联。

几处原版 AArch64 指令的准确直接比较链（地址都是 NSO text RVA）：

| 读取 PC | 原始读取 | 紧接着的比较 | 证据级别 |
| --- | --- | --- | --- |
| `0x03B428` | `ldrb w8,[x8,#0x26]` | `0x03B42C: cmp w8,#0xF` | 寄存器直达立即数比较，源指针经过 `csel`，尚未关联 00983 |
| `0x0BA9F8` | `ldrb w9,[x2,#0x26]` | `0x0BA9FC: cmp w9,#4` | 同上 |
| `0x1B9284` | `ldrb w8,[x27,#0x26]` | `0x1B9288: cmp w8,#4` | 同上 |
| `0x1BA9EC` | `ldrb w8,[x21,#0x26]` | `0x1BA9F0: cmp w8,#6` | 同上 |
| `0x332384` | `ldrb w9,[x9,#0x26]` | `0x332388: cmp w9,#0xF` | 同上 |

**真实推进结果**：已经证明多个原始 `+0x26` **字节读取确实进入分支条件**，比 M9 的“同位移候选”更进一步；但是 AArch64 内存在多种无关结构共享偏移 `0x26`，不能因此把 `+0x26=0x10` 命名为材料类，也不能将 `cmp #0xF` 当成食物分类证明。

### 后续最值得执行的跨函数跟踪

- 从 `0x03B428` 的 `csel x8,x9,x8,eq` 两个来源出发，逆向确定对象分配/解析路径，不能只扩大附近汇编窗口。
- 对 `0x0BA9F8`、`0x1B9284` 等 `cmp #4` 做 caller xref/对象结构来源比对：只有确认 68 字节 Item 记录基址才允许解释为物品分类。
- 独立追踪 `cmp #99/#100` 对应的数量变量来源与 `strb Count` 写回；目前 M11.1 的六处结构共访问没有一处同窗口 99/100 判断，不能把 99 上限当作已恢复的原版指令链。

## M11.3 原生 983 ID 查询链：双路径指令级确认

直接扫描原版 ExeFS 全文发现装入 `movz #983` 的十处地址，并重点检查是否作为调用参数，而不把任何立即数 `983` 自动称为 LINKDATA 条目号。

两条**原字节已确认**的路径：

```asm
main+0x14FD9B0  mov  w0, #0x3D7       ; 983
main+0x14FD9B4  bl   0x1445E30
main+0x14FD9B8  bl   0x14718F0
main+0x14FD9BC  adrp x8, 0x36D5000
main+0x14FD9C0  str  x0, [x8, #0x4C8] ; global RVA 0x36D54C8

main+0x14FDB1C  mov  w0, #0x3D7
main+0x14FDB20  bl   0x1445E30
main+0x14FDB24  bl   0x14718F0
main+0x14FDB28  adrp x8, 0x36D5000
main+0x14FDB2C  str  x0, [x8, #0x4C8]
```

`main+0x1445E30` 是原生 ID 索引函数：函数中对 `w0` 执行 `cmp #0x4AA`（遇无符号超范围跳分支）；随后使用 `mov w9,#0x28` 和 `umaddl x9,w0,w9,x8` 按 **40 字节描述符步长**读取内部表，访问每个描述符 `+0x10` 的 `u32` 值。其索引有效范围在当前路径为 `0..1194`，不等于原始物品表的 `0..4599`，更不等于物品记录步长 68。

**结论分层：**

- 已证实：字面值 `983` 进入两段直接调用链，经过 40 字节描述符索引函数，再调用包装函数并保存全局返回指针。
- 未证实：该输入 ID 属于 LINKDATA 的 `00983.bin` 名称空间；全局 `0x36D54C8` 指向 `00983.bin` 内容；加载后的表是否在另一层完成了 4600×68 原生记录解码。
- 原版 `ADRP+LDR/STR` 对全局的直接扫描目前仅找到上述两条 `STR`（非 `LDR`）；可能由对象基址、偏移变形或其它访问路径读取，所以不能据此判定该全局“未使用”。

`Scripts/resources/trace_native_item_resource_loader.py` 固定核验这 2 条 983 链、原始 40 字节描述符结构，并列出全局直接访问及两个 callee 的汇编证据。结果位于 `literal983_global_provenance.json`。下一轮应追 `0x14718F0` 后继函数到实际解包指针，并寻找 `0x36D54C8` 经间接对象基址访问的消费者；只有与原始 00983 内容、记录基址和 ItemID 计算同时闭合，才可升级物品分类、材料、堆叠数等实际字段语义。
