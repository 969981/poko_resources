# Pokopia 2.0.1 — 原生物品分类与数量上限：候选地址复核

依据：原版 `2.0.1/exefs/main` SHA-256 `8a8ce87b4edfce88c6260da5dd80d6cafc03a761eebc842d7a3476e353a8336f`；原版 `00983.bin` SHA-256 `2a2dbc88715dc76410cef495d418613456c0c4fa7b7d719e7b37709ad53e1b6f`。

## 已验证

- 物品表 `00983.bin` 为 64 字节表头 + 4,600 × 68 字节，`+0x22` 名称索引有九语言对账。
- 可执行代码确有访问 `+0x26`、`+0x3A` 的 ARM64 指令和比较 99/100 的指令。
- 但指令偏移匹配并不证明基址来自这份 68 字节物品表，也不证明比较值是物品堆叠上限。

## 候选代码反证与待验收结论

1. `main+0xA40A44` 读取 `[x25,#0x3A]`，随后比较 12；`main+0xA40A5C` 附近比较 99。原始物品表 **3,585 条有名称记录** 的 `+0x3A` 原始值有 0、1、2、6、7、8、13、14、15、18、21，没有 12。它**不是已证实的物品分类或堆叠上限读取点**；对无名称记录及不同运行时编码尚未完成排除。
2. `main+0x265F48` 读取 `+0x26`；`main+0x265F5C` 比较 100。但参加 100 比较的寄存器由 `[x19,#0x20]` 减一而来，当前没有证据表明它属于物品数量。
3. `main+0x1C69B4/+0x1C69C0/+0x1C69C8` 依次读取 `+0x22/+0x24/+0x26` 的 16 位值，并执行 `BFI/ORR` 位域打包；这种 `+0x26` 命中也不能证明物品类型。
4. `main+0x54D7AC` 虽比较 100，但其上下文是以 2 递增的循环计数器，不应认定是堆叠上限。

## 真实定位需要的证据链

`00983.bin（4,600×68） → 原生表加载/记录基址 → 物品 ID 索引 → 读取 +0x26 / +0x3A → 消费该枚举的真实调用者`。

数量上限应另行验证：

`背包添加 → 匹配旧物品堆 → 剩余容量计算 → 99/100 比较 → 余数开新堆或拒绝 → 实际存档数量写回`。

**截至本阶段：官方分类枚举、逐物品堆叠上限、背包槽位上限和可用 Hook 地址均未完成证明。** `PokoHex` 的 1 字节数量字段只能证明 0–255 的数值表示范围，不代表实际允许堆叠 255。请勿将 99 填入各物品的原生属性字段。

原始反汇编和统计详见 `item_assembly_candidates.json`、`item_assembly_focus.json`、`ITEM_ASSEMBLY_RESEARCH.md`。
