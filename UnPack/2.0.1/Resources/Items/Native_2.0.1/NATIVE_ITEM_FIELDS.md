# Pokopia 2.0.1 — 原生物品分类与数量字段核验

> 数据源：当前分支原版 RomFS 解包结果，不是从第三方中文网页重新生成的分类。

## 已有直接证据

- 原始 LINKDATA 条目：`UnPack/2.0.1/romfs/LD_C0_R.BIN/decoded/00983.bin`
- SHA-256：`2a2dbc88715dc76410cef495d418613456c0c4fa7b7d719e7b37709ad53e1b6f`
- 二进制结构：64 字节表头（`count=4600, version=3`）+ 4600 条 × 68 字节。
- 名称索引位于记录 `+0x22`（小端 u16），匹配当前分支九语言原生文本对账。
- `+0x26` 是**物品细分类型候选**，不是已确认的官方枚举名称。 `+0x3A` 等字节表现为另一类分组，暂保留原值。

## 数量上限：不能把三个不同概念混淆

1. **原生物品表中的逐物品最大堆叠数**：尚未证明位于 `00983.bin` 的哪个字段，也未证明原生表按物品分别配置，CSV `native_max_stack` 故意留空。
2. **正常游戏内堆叠数**：GameSpot 记载普通背包及储物箱每组最多 **99**；这是独立的游戏玩法来源，**不是原始字节解析结论**：https://www.gamespot.com/articles/how-to-increase-storage-space-in-pokemon-pokopia/1100-6538594/
3. **存档数值表示范围**：PokoHex 的 `PokoHex.Core/Structures/Item.cs` 将一个物品槽定义为 5 字节，其中数量为 `byte Count`，理论保存范围为 **0–255**。这不能证明游戏内物品可正常叠放 255 个：https://github.com/969981/PokoHex/blob/main/PokoHex.Core/Structures/Item.cs

`+0x08` 的 u32 在食品和矿石中经常为 10、50、100、200、500、2000 等，**很像价值/价格**，不得将其当作最大数量字段。

背包槽位数、容器槽位数也属于另外的容量概念，不是单个物品叠加上限。

## 可复现产物

- `native_item_raw_fields.csv`：4,600 条记录，保存中英文名称、候选字段、未解释的 68 字节原始十六进制和空的逐物品最大堆叠字段。
- `native_item_field_analysis.json`：候选字段频次和逐组示例，来源及数量上限的证据分级。
- `Scripts/resources/analyze_native_item_fields.py`：从本分支原始文件重建上述两类报告（哈希、大小、版本检查）。

执行：

```bash
python Scripts/resources/analyze_native_item_fields.py
```

## 下一步验证

- 对 `0x26`、`0x3A` 做原生调用点/枚举表交叉引用，确认哪一个代表背包分类、展示/建造分组或放置类型。
- 从 `2.0.1/exefs/main` 静态分析物品入包、堆叠合并、拆分、存档写入代码，追踪 **99**、**255** 对应的边界检查；不能用魔数出现次数作为命中证明。
- 检查物品是否存在不同堆叠规则或仅全局 99 上限；用至少三个物品类别的游戏运行时行为做交叉验证。
- 若发现原版按物品配置数量，再新增 `max_stack_native` 和 `max_stack_evidence_path/offset`；没有证据不得填默认 99 伪装成逐项原生数据。
